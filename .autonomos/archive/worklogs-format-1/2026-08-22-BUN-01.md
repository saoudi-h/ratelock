# Worklog — 2026-08-22 — BUN-01

## What was done

Evaluated Bun 1.4.0 native clients (`RedisClient`, `SQL`) as storage drivers for `@ratelock/redis` and `@ratelock/postgres`, via executable PoCs run against the project's real Docker test services (Redis 6380, Postgres 5434) using the REAL strategy code and REAL Lua/SQL.

Environment: upgraded local bun 1.3.14 → 1.4.0 (`bun upgrade`). Built all packages fresh (`pnpm build`, 7/7 green).

### Redis PoC — ALL GREEN (16/16)

Approach: node-redis-compatible shim (~60 lines) over `Bun.RedisClient` — passes `detectDriver` via an `isOpen` property, maps node-redis calling conventions onto `client.send(cmd, args)`.

Verified through all four strategy factories: fixed window (limit/deny/reset), sliding window (real `windowStart` from Lua oldest-ts), token bucket (clean drain 4→3→2→1→0→deny, refillTime correct), individual fixed window (window rollover), batch ops per-id, direct EVALSHA round trip.

Key API mappings proven:
- Lua: `send('EVAL'|'EVALSHA', [script|sha, keyCount, ...keys, ...args])`; script load: `send('SCRIPT', ['LOAD', lua])`
- Pipelines: Bun auto-pipelines concurrent commands (`enableAutoPipelining` default on) → our `pipeline()` abstraction = queue + `Promise.all`
- URL auth works (`redis://:pass@host:port`); RESP2 conversions (integers, arrays, bulk strings) match what strategies expect
- Gotcha: adapter pipelines pass node-redis style `{keys, arguments}` option objects to the shim, not positional args

### Postgres PoC — ALL GREEN after one real fix

Approach v1: pass `new SQL(url)` directly as the existing `sql` option → single checks worked with ZERO adapter code (Bun SQL is postgres.js-shaped: `unsafe()`, `reserve()`, `end()`). `checkBatch` crashed: JS array params are not serialized to Postgres array literals.

Approach v2: thin `bunDriver(sql)` (same BEGIN/COMMIT-reserve shape as `drivers/postgres.ts`) + manual text[] serialization:
`'{' + values.map(v => '"' + v.replace(/\\/g,'\\\\').replace(/"/g,'\\"') + '"').join(',') + '}'`

**Important discovery:** Bun 1.4.0's own `sql.array()` emits broken element quoting (`"x"` becomes literal quotes inside text[] elements). Silent data pollution risk: sliding-window batches "passed" while writing quoted keys — only caught because I added per-key state assertions. Manual literals are mandatory until fixed upstream.

Also surfaced a pre-existing engine issue (driver-independent): duplicate ids in `checkBatch` take a dedup fallback implemented as `Promise.all(ids.map(check))` — concurrent same-key upserts return nondeterministic result mappings ([1,2,2] vs postgres.js's [2,2,1]; final DB state always correct; sequential loop gives deterministic [2,2,1]). postgres.js masked this; Bun SQL exposed it. Registered as CORE-02 (sequential fallback fix).

## Decision

**Internalize native Bun support into existing packages — no dedicated @ratelock/bun-* packages.** Consistent with the 2026-05-19 decision log ("add driver support to existing adapters first"). Both PoCs prove feasibility with thin adapters (<70 lines each):

- BUN-02: `'bun'` driver in `@ratelock/redis` (`client.ts`: extend union, detection branch, loadFromUrl path)
- BUN-03: `drivers/bun.ts` in `@ratelock/postgres` (+ manual array serialization)
- CORE-02: sequential dup-batch fallback (engine-wide correctness)

Watch items: upstream `sql.array()` quoting bug; Bun client is 1.4-fresh (API stability risk low but non-zero).
