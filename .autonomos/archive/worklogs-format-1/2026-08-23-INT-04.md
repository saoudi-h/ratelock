# Worklog — 2026-08-23 — INT-04 (http-common extraction)

## What was done

Rule of three reached after three framework integrations; extracted the duplicated logic.

- New private package `packages/http-common` (`private: true`, never published): `createLimiterResolver`, `projectResult`, `collectRateLimitHeaders`, shared types (`HeadersMode`, `HeaderInfo`, `LimiterInput`) + 10 unit tests.
- Consumers (hono/express/fastify) list it as a **devDependency**: tsdown externalizes dependencies/peers but bundles devDeps, so the shared code inlines into each published dist. Verified empirically: zero `@ratelock/http-common` references in all three dist/index.mjs, shared symbols present.
- Design decision: tiny type definitions (`HeadersMode`, `LimiterInput`) stay LOCAL to each middleware so generated .d.ts files never reference the private package (which would break consumers). Only runtime logic is shared.
- Header application stays per-framework via `collectRateLimitHeaders` returning a plain record each adapter iterates with its own setter (`c.header` / `res.setHeader` / `reply.header`).
- Public APIs unchanged; no changeset (internal refactor, policy: changesets for user-facing changes only).

PR #17 merged, all checks green. No npm publish (no changesets).

## Key decisions

- Bundled-private pattern chosen over publishing an internal package or polluting @ratelock/core (maintainer agreed earlier that core must keep its contracts+decorators boundary).
- http-common has its own test suite; future integrations (elysia, web helper) consume it from day one.
